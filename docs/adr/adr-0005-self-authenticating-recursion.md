# Status

Accepted

# Context

To prove validation across the hundreds of thousands of Bitcoin block headers without exceeding prover memory or time limits, `zkpow` structures proof generation as an Incrementally Verifiable Computation (IVC) chain. In this model, proving batch $B_{i}$ (covering block heights $H_{k} \dots H_{m}$) must inductively prove:

1. The batch transition from state $S_{i-1}$ to $S_{i}$ under candidate headers is consensus-valid.
2. The starting state $S_{i-1}$ was itself attested by a valid cryptographic proof $\Pi_{i-1}$ extending from the Bitcoin genesis anchor.

In the SP1 zkVM, recursive proof verification is performed via the syscall `sp1_zkvm::lib::verify::verify_sp1_proof(vk_digest: &[u32; 8], pv_digest: &[u8; 32])`. This syscall verifies that a proof object provided in the auxiliary proof witness stream was generated by the program identified by `vk_digest` and committed public values whose SHA-256 digest equals `pv_digest`.

This presents two fundamental design challenges:

1. **State forgery & proof extension attacks**: A prover provides both the starting state $S_{i-1}$ and the previous proof $\Pi_{i-1}$ as unconstrained inputs. If the guest directly parsed previous public values out of an untrusted witness buffer, a prover could attempt to extend a forged state or extend a proof that had terminated in a consensus error (such as a Tier 2 rejection proof).
2. **Key self-introspection inside zkVM**: A guest program executing inside RISC-V cannot introspect its own verifying key or circuit parameters at runtime without hardcoding a circular dependency (as changing the program changes its own ELF and verifying key).
3. **In-circuit recursion overhead**: Deserializing, parsing, and verifying structured proof objects inside the guest circuit consumes substantial zkVM cycles.

We must define how the guest authenticates its prior state and verifying key across recursive boundaries with minimal cycle overhead and airtight cryptographic soundness.

# Decision

In `crates/guest/src/main.rs`, verify the previous recursive step $\Pi_{i-1}$ by **reconstructing** the expected previous 185-byte `PublicValues` directly from the guest's own input arguments, hashing them with the optimized `zkpow_sha256::of_public_values` helper, and asserting that the return code byte is **strictly** `ReturnCode::SUCCESS (0)`:

```rust
let actual_pv_hash = zkpow_sha256::of_public_values(
    state.as_bytes(),
    verifier_key.as_bytes(),
    ReturnCode::SUCCESS.into_u8(),
);
sp1_zkvm::lib::verify::verify_sp1_proof(verifier_key.as_raw(), &actual_pv_hash);
```

Specifically:

1. **Reconstruction over parsing**: The guest never receives, reads, or parses the previous proof's public values. Instead, it synthesizes the exact canonical 185-byte layout:
   $$\text{Preimage} = \text{State}_{i-1} \,\|\, \text{VerifierKeyDigest} \,\|\, \text{ReturnCode::SUCCESS} \, (0)$$
2. **Hardcoded success assertion**: The return code byte in the reconstructed preimage is hardcoded to `0` (`ReturnCode::SUCCESS`).
3. **Untrusted key threading with verifier anchoring**: The guest accepts `verifier_key` as an untrusted input argument, uses it to verify the prior proof, and commits that exact same key unchanged into its own output `PublicValues`.
4. **Genesis base case ($H = 0$)**: When `state.height == 0`, recursion is skipped. The state is accepted as the trusted genesis anchor.

# Soundness Proof & Security Analysis

### 1. Impossibility of State Forgery
Let $\Pi_{i-1}$ be a valid SP1 proof generated by a program with verifier key $VK$, committing public values $PV_{i-1}$.
By definition of the SP1 recursion circuit, `verify_sp1_proof(VK, digest)` accepts if and only if:
$$\text{digest} = \text{SHA-256}(PV_{i-1})$$

In batch $B_i$, the guest computes:
$$\text{digest} = \text{SHA-256}(S_{\text{input}} \,\|\, VK_{\text{input}} \,\|\, 0)$$

By collision resistance of SHA-256, `verify_sp1_proof` will fail unless the actual public values committed by $\Pi_{i-1}$ match byte-for-byte:
$$PV_{i-1} = S_{\text{input}} \,\|\, VK_{\text{input}} \,\|\, 0$$

Therefore, a prover cannot alter a single bit of $S_{\text{input}}$ (chain work, tip block hash, difficulty bits, epoch timestamp, or MTP ring) without causing `verify_sp1_proof` to fail. The input state is mathematically bound to the previous proof's committed output.

### 2. Impossibility of Extending Rejection / Fraud Proofs
As defined in [ADR-0004](file:///Users/tcrypt/code/github.com/tcrypt25519/bitcoin-header-chain/docs/adr/adr-0004-four-tier-guest-termination-taxonomy.md), a consensus rejection proof commits a non-zero `ErrorCode` ($E \in \{2, 3, 5\}$). Its committed public values are:
$$PV_{\text{rejection}} = S_{\text{valid}} \,\|\, VK \,\|\, E \quad \text{where} \quad E \ne 0$$

When a prover attempts to supply $PV_{\text{rejection}}$ as the recursive witness for batch $B_i$:
- The guest reconstructs:
  $$H_{\text{expected}} = \text{SHA-256}(S_{\text{valid}} \,\|\, VK \,\|\, 0)$$
- But the proof $\Pi_{\text{rejection}}$ commits:
  $$H_{\text{actual}} = \text{SHA-256}(S_{\text{valid}} \,\|\, VK \,\|\, E)$$

Because $E \ne 0$, $H_{\text{expected}} \ne H_{\text{actual}}$. The `verify_sp1_proof` circuit constraint is unsatisfied.
**Conclusion**: A consensus rejection proof is an absolute terminal leaf. It can never be extended, ensuring invalid chains cannot be continued.

### 3. Soundness of Untrusted Verifier Key Threading
Because the guest cannot know its own circuit verifying key, it accepts $VK$ as an input and commits $VK$ in its public values.
Suppose an attacker supplies a foreign program key $VK_{\text{malicious}}$ and a valid proof $\Pi_{\text{fake}}$ produced by that foreign program.

1. **Step $1 \to 2$**: The guest verifies $\Pi_{\text{fake}}$ against $VK_{\text{malicious}}$. This passes, but the guest commits $VK_{\text{malicious}}$ into $PV_2$.
2. **Step $k-1 \to k$**: By induction, every subsequent recursive step verifies against the input key and commits that same key. Therefore, the final proof $\Pi_{\text{final}}$ commits:
   $$PV_{\text{final}}.\text{verifier\_key} = VK_{\text{malicious}}$$

**The Verifier Boundary**:
An end-user or smart contract verifier checking $\Pi_{\text{final}}$ performs two checks:
1. Verify the SP1 proof $\Pi_{\text{final}}$ against the trusted canonical guest verifying key $VK_{\text{canonical}}$.
2. Check that the committed field $PV_{\text{final}}.\text{verifier\_key} == VK_{\text{canonical}}$.

If an attacker substituted a malicious key anywhere in the historical chain, either:
- The proof verification fails (if verifying against $VK_{\text{canonical}}$), OR
- The committed $PV.\text{verifier\_key}$ matches $VK_{\text{malicious}} \ne VK_{\text{canonical}}$, and the verifier rejects the proof.

Thus, verifying the key once on the final proof inductively authenticates the program identity of every batch all the way back to genesis.

# Consequences

### Positive
- **POS-001: Zero witness parsing in-circuit**: The guest never parses previous proof bytes or public value structures. It reads raw bytes via zero-copy casts and hashes them directly into the syscall.
- **POS-002: Provable terminal leaf for rejections**: Enforces that only chains where every previous header was 100% valid can be advanced.
- **POS-003: Eliminates cyclic key dependencies**: The guest binary does not need to know its own verifying key, enabling reproducible guest compilation without multi-pass key injection.
- **POS-004: Unified public value format**: Both batch 1 (from genesis) and batch $N$ commit the exact same 185-byte `PublicValues` structure, simplifying verifier implementations.

### Negative
- **NEG-001: Strict layout coupling**: Any modification to `State` (even field order) changes the 185-byte serialization and invalidates recursive proof verification across existing stored proofs.
- **NEG-002: Verifier responsibility**: External verifiers *must* explicitly assert that the committed `verifier_key` in public values matches their expected key; verifying the SP1 wrapper alone without checking the inner committed key allows key-substitution if wrapping proofs under generic provers.

# Alternatives Considered

### Option 1: Pass previous public values as a witness buffer and parse them
- **Description**: Prover inputs `previous_pv: Vec<u8>`. Guest deserializes `previous_pv`, extracts `state`, asserts `return_code == 0`, and hashes `previous_pv` for `verify_sp1_proof`.
- **Rejection Reason**: Adds redundant buffer allocations, deserialization logic, and field copying inside the circuit. Reconstructing from `&State` directly uses memory already resident in the guest's input slice.

### Option 2: Hardcode the verifying key digest into the guest binary
- **Description**: Precompute the guest verifying key and embed it as a `const [u32; 8]` in `guest/src/main.rs`.
- **Rejection Reason**: Creates an impossible circular build dependency: compiling the guest changes its ELF binary, which changes its verifying key, which would change the source code and require recompilation.

### Option 3: Allow extending failure proofs with error propagation
- **Description**: Allow batch $i$ to extend a failed batch $i-1$, propagating the error code forward.
- **Rejection Reason**: Meaningless and dangerous. A chain that failed consensus is dead; allocating compute to extend an invalid chain wastes prover resources and complicates verifier semantics.
