# Specification: zkpow

## 1. Consensus Verification Scope

zkpow implements Bitcoin proof-of-work consensus according to the original protocol rules defined in the initial Bitcoin release, without checkpoints or retroactive soft-fork header restrictions.

### 1.1 Evaluated Rules

1. **Proof of Work:** For every block header, the double-SHA-256 hash of the 80-byte header must be less than or equal to the active target:
   $$\text{SHA256}(\text{SHA256}(\text{header})) \le \text{target}$$
2. **Median Time Past (MTP):** The header timestamp must be strictly greater than the median of the previous 11 block timestamps:
   $$\text{timestamp} > \text{MTP}_{11}$$
3. **Difficulty Adjustment Schedule:** Difficulty adjusts every 2,016 blocks. The retarget calculation evaluates the actual timespan of the preceding 2,015 blocks:
   $$\text{actual\_timespan} = t_{\text{epoch\_end}} - t_{\text{epoch\_start}}$$
   The timespan is clamped to the range $\left[\frac{\text{target\_timespan}}{4}, \text{target\_timespan} \times 4\right]$ (between 3.5 days and 8 weeks), multiplied by the previous target, capped at `MAX_TARGET` (`0x1d00ffff`), and truncated through the compact 32-bit `nbits` representation.
4. **Cumulative Work Accumulation:** Chain work accumulates monotonically per difficulty epoch:
   $$\text{work}_{\text{block}} = \left\lfloor \frac{2^{256}}{\text{target} + 1} \right\rfloor$$
   $$\Delta \text{chain\_work} = \text{work}_{\text{block}} \times N_{\text{headers\_in\_segment}}$$
5. **Cold Start Window:** The first 10 blocks following genesis are validated using the genesis difficulty target and a partial sorted timestamp window.

### 1.2 Excluded Rules

- **Checkpoints:** The guest contains no hardcoded block hashes beyond the mainnet genesis block hash.
- **BIP34 (Coinbase Height):** Not evaluated; transaction contents are not parsed within the header validation guest.
- **BIP66 / BIP68 / Version Restrictions:** Header version numbers are treated as arbitrary 32-bit fields; negative versions (e.g., version 3+ conventions) are permitted if proof-of-work and MTP conditions hold.

## 2. Public Values Specification (185-Byte Interface)

Every SP1 proof generated by zkpow commits exactly 185 bytes of public values.

### 2.1 Memory Layout

| Byte Offset | Size (Bytes) | Field Name | Type | Description |
| :--- | :--- | :--- | :--- | :--- |
| `0..32` | 32 | `chain_work` | `[u8; 32]` | Cumulative chain work in big-endian representation |
| `32..64` | 32 | `genesis_hash` | `[u8; 32]` | Mainnet genesis block hash (network identifier) |
| `64..96` | 32 | `block_hash` | `[u8; 32]` | Block hash of the tip header accepted by this proof |
| `96..100` | 4 | `height` | `u32` (LE) | Tip block height |
| `100..104` | 4 | `current_nbits` | `u32` (LE) | Active compact difficulty bits for the current epoch |
| `104..108` | 4 | `epoch_timestamp`| `u32` (LE) | Timestamp of the first block of the current 2,016 epoch |
| `108..152` | 44 | `timestamps` | `[u32; 11]` (LE) | Ring buffer of the last 11 block timestamps |
| `152..184` | 32 | `verifier_key` | `[u8; 32]` | SP1 Verifier Key (vk) digest of the guest program |
| `184..185` | 1 | `return_code` | `u8` | Status code (`0` indicates success) |

### 2.2 Return Codes

| Code | Label | Description |
| :--- | :--- | :--- |
| `0` | `SUCCESS` | All headers in the batch verified validly against consensus rules. |
| `2` | `ERR_POW_INVALID` | Block header hash exceeded the active difficulty target. |
| `3` | `ERR_MTP_INVALID` | Block header timestamp was less than or equal to median time past. |
| `5` | `ERR_COLD_WINDOW` | Initial batch contained fewer than 10 headers required for cold start. |

Proofs with a non-zero return code are valid cryptographic proofs of consensus rejection; however, the recursion induction step rejects non-zero proofs.

## 3. Guest Input Stream Protocol

The prover feeds data to the guest via standard input (`sp1_zkvm::io::read`):

1. **Previous Proof Witness (Optional for Genesis):**
   - Present when `height > 0`.
   - The guest reconstructs the expected 185-byte public values buffer using the incoming `State`, its own program `verifier_key`, and `return_code = 0`.
   - The guest computes $\text{SHA256}(\text{reconstructed\_pv})$ and executes:
     `sp1_zkvm::lib::verify_sp1_proof(&verifier_key, &pv_hash);`
2. **Batch Headers (Compressed Format):**
   - Headers are supplied as 44-byte slices:
     - `version` (4 bytes, LE)
     - `merkle_root` (32 bytes)
     - `timestamp` (4 bytes, LE)
     - `nonce` (4 bytes, LE)
   - `prev_blockhash` is bound directly from the active `State.block_hash`.
   - `nbits` is bound directly from the active `State.current_nbits`.
3. **Median Hints (Sparse Stream):**
   - Supplied only for block heights where timestamps are not monotonically non-decreasing.
   - Checked in-guest via $O(11)$ count scan: must have exactly 5 elements below and 5 elements above/equal. Extra or missing hints trigger an immediate zkVM exit.

## 4. Batch Sizing and Execution Performance

- **Supported Batch Sizes:** 2,016 (default 1 epoch), 4,032 (2 epochs), and 8,064 (4 epochs).
- **Proving Growth Characteristic:** Proving time exhibits sublinear scaling across batch sizes up to 8,064 headers (~50% increase in wall-clock proving time per doubling of batch size).
- **Update Frequency:** Pipeline executes batches on regular intervals (~hourly or per epoch) to maintain currency with the Bitcoin chain tip.

## 5. Verification Interfaces

### 5.1 SP1 Native Verification
Consumers verifying the recursive compressed proof directly check:
1. Proof verification against the known guest `verifier_key`.
2. Committed `genesis_hash == 000000000019d6689c085ae165831e934ff763ae46a2a6c172b3f1b60a8ce26f`.
3. Committed `verifier_key == expected_vkey`.
4. Committed `return_code == 0`.

### 5.2 EVM Groth16 Verification
For smart contract integration, SP1 wraps the final recursive proof into a Groth16 SNARK. Verification interfaces directly with standard Succinct SP1 verifier contracts (`ISP1Verifier.verifyProof(vkey, publicValues, proofBytes)`), requiring zero custom bridge contracts or custom verifier deployment.
